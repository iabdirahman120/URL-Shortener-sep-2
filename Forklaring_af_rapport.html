Forklaring af SEP2 rapport

URL Shortener — shr.dk  ·  Gennemgang af alle afsnit i rapporten

Afsnit 1

Introduktion

Introduktionen er den første tekst eksaminatoren læser. Den skal på kort tid svare på: hvad er projektet, hvem har lavet det, og hvad er formålet?

Hvad beskriver introduktionen?

  • Systemets navn: shr.dk — en URL Shortener
  • Hvad systemet gør: Konverterer lange URL-adresser til korte, delbare links
  • Konteksten: Udviklet som SEP2-projekt i samarbejde med virksomheden ZNG
  • Teknologistakken: Node.js backend, React frontend, PostgreSQL database
  • Kommunikation: HTTP REST API med JWT-autentificering

Sådan kan du forklare det til eksamen:

"Projektet hedder shr.dk og er et URL-forkortelses-system. Systemet er bygget som et client/server system, hvor en React-frontend kommunikerer med en Node.js/Express-backend via HTTP. Alt data — brugere, links, klik — gemmes i en PostgreSQL-database. Brugere autentificeres med JWT-tokens."

Afsnit 2

Problemformulering

Problemformuleringen er udgangspunktet for hele projektet. Den skal definere det problem du løser — og stille det som et præcist spørgsmål.

Problemet

Lange URL-adresser er svære at dele — de fylder for meget i SMS, sociale medier og trykt materiale. Et URL-forkortelses-system løser det ved at erstatte lange adresser med korte links, der automatisk viderestiller besøgende.

Den centrale problemstilling i rapporten

"Hvordan kan man designe og implementere et sikkert client/server system, der effektivt genererer, gemmer og håndterer forkortede URL-links — med brugerkonti, statistik, adgangskodebeskyttelse og administrationspanel?"

Til eksamen — forbind problemet med løsningen:

"Problemet er, at lange URLs er svære at dele. Løsningen er et system, der genererer korte koder og gemmer en mapping fra kode til original URL i databasen. Når nogen besøger det korte link, slår serveren koden op og redirecter automatisk."

Afsnit 3

Krav

Kravene er fundamentet som resten af projektet bygger på. Eksaminatoren vil tjekke om dine krav hænger sammen med din implementation og dine tests.

Funktionelle krav (FK)

Hvad er et funktionelt krav?

Et funktionelt krav beskriver hvad systemet skal kunne gøre — altså en konkret funktion eller adfærd set fra brugerens synspunkt.

Eksempler fra rapporten:

  • FK-03: Bruger kan forkorte en lang URL og modtage et kort link
  • FK-04: Systemet viderestiller besøgende fra kort link til original URL
  • FK-07: Bruger kan se klikstatistik (daglige klik, enhed, referrer)

Ikke-funktionelle krav (IFK)

Hvad er et ikke-funktionelt krav?

Et ikke-funktionelt krav beskriver hvordan systemet skal opføre sig — kvaliteter som sikkerhed, ydeevne og pålidelighed. Det er ikke en funktion, men en egenskab.

Eksempler fra rapporten:

  • IFK-01: Adgangskoder hashes med bcrypt — gemmes aldrig i klar tekst (sikkerhed)
  • IFK-03: SQL-forespørgsler bruger parameteriserede queries (sikkerhed mod SQL injection)
  • IFK-04: Redirect sker inden for 500 ms (ydeevne)

Til eksamen — forskel på FK og IFK:

"Funktionelle krav siger hvad systemet gør — fx at man kan forkorte en URL. Ikke-funktionelle krav siger hvordan — fx at adgangskoder altid hashes med bcrypt og aldrig gemmes i klar tekst."

Hvorfor er krav vigtige i SEP2?

SEP2 kræver en tydelig sammenhæng: krav → use cases → design → implementation → test. Hvert krav skal kunne spores hele vejen igennem. FK-03 (forkorte URL) fører til UC3 (Use Case), som fører til POST /api/urls/shorten (implementation), som fører til TC-05 (test).

Afsnit 4

Scrum-proces

Scrum er en agil udviklingsmetode. I dette projekt er det tilpasset til soloarbejde, men strukturen er fulgt: product backlog, sprints, reviews og retrospectives.

De tre Scrum-roller (i dette projekt varetaget af én person)

  • Product Owner: Prioriterer hvad der skal laves. Beslutter hvilke user stories der er vigtigst.
  • Scrum Master: Sikrer at processen følges. Fjerner forhindringer.
  • Developer: Implementerer løsningen.

De tre faser i projektet

  • Sprint 0 (uge 1–2): Analyse og planlægning — videnssøgning, krav, use cases, diagrammer. Ingen kode.
  • Sprint 1 (uge 3–4): Backend og database — register, login, URL-forkortelse, redirect, dashboard API.
  • Sprint 2 (uge 4–5): Frontend og avancerede funktioner — React UI, statistik, admin panel, password-links, email-reset.

Product Backlog og User Stories

Hvad er en User Story?

En user story beskriver en funktion set fra brugerens perspektiv i formatet:

"Som [rolle] vil jeg [handling], så jeg [formål]"

Eksempel: "Som bruger vil jeg forkorte en URL, så jeg kan dele korte links"

Hvad er Story Points overhovedet?

Story points (SP) er en måde at sætte et tal på, hvor svær og tidskrævende en user story er — men ikke i timer. Det er et relativt tal: vi sammenligner user stories med hinanden og siger "den her er dobbelt så svær som den der".

Forskellen fra timer er vigtig: timer afhænger af, hvem der laver opgaven og hvor hurtig de er den dag. Story points handler om kompleksitet i sig selv — uanset hvem der koder det.

Skalaen — Fibonacci-tal

Story points bruges typisk med Fibonacci-tal: 1, 2, 3, 5, 8, 13... Grunden er, at jo større en opgave er, jo sværere er det at estimere præcist. Fibonacci-tal tvinger os til at vælge klart — i stedet for at sige "3 eller 4" skal vi vælge enten 3 eller 5.

I dette projekt brugte vi kun 1, 2, 3 og 5 fordi ingen opgave var enormt stor.

SPHvad det betyderEksempel fra projektet
1Triviel. Én simpel operation, ingen logik at tænke over.US-06: Slet link — ét SQL-kald: DELETE FROM urls WHERE id = $1
2Lille. Et par trin, men ingen kompleksitet.US-02: Login — query + tjek password + lav JWT token
3Medium. Flere dele der hænger sammen, lidt at tænke over.US-01: Register — validering + bcrypt hashing + database insert + fejlhåndtering
5Stor. Kompleks logik, mange komponenter, svær at overskue.US-07: Statistik — 3 parallelle SQL-queries, dato-gap-udfyldning, device-parsing, referrer-parsing, chart i frontend

Hvordan finder man et story point-tal? (Processen)

Man starter med at finde referenceopgaven — den simpleste opgave man kan forestille sig. Her er det US-06 (slet link), som får 1 SP. Herefter estimerer man alle andre opgaver i forhold til den:

  • "Slet link er 1. Login er lidt sværere — der er et par trin mere. Jeg siger 2."
  • "Register er sværere end login fordi der er bcrypt-hashing og unique constraint at håndtere. Jeg siger 3."
  • "Statistik er meget sværere end register. Der er 3 database-queries, dato-logik og chart. Jeg siger 5."

Man placerer ikke et tal først og begrunder det bagefter — man sammenligner og lander på et tal.

Hvorfor bruger man story points og ikke bare timer?

Fordi tidsestimater er notorisk unøjagtige i softwareudvikling. En erfaren udvikler bruger måske 30 minutter på login, en studerende bruger 3 timer. Story points handler om kompleksitet, ikke om hvem der koder det.

Derudover er det nemmere at sammenligne relativt: "den her er dobbelt så svær som den der" er meget lettere at vurdere end "den her tager præcis 4 timer og 23 minutter".

Til eksamen — sådan forklarer du det:

"Story points er en relativ vurdering af kompleksitet, ikke timer. Jeg startede med at finde den simpleste opgave — slet link, som fik 1 SP. Derefter estimerede jeg alle andre stories i forhold til den. Jo flere dele der hænger sammen, jo flere points. US-07 statistik fik 5 SP fordi den krævede 3 parallelle database-queries, dato-logik for at udfylde huller i 30 dage, parsing af user-agent for enhedstype, og en chart-komponent i frontend — langt den mest komplekse feature."

Burndown Chart

Hvad viser et burndown chart?

Et burndown chart viser, hvor mange story points der er tilbage over tid i et sprint.

  • Y-aksen: Resterende story points
  • X-aksen: Dage i sprintet

Use Case Beskrivelser

Hvad er en use case beskrivelse?

En detaljeret gennemgang af én use case. Den indeholder:

  • Aktør: Hvem gør det
  • Forudsætning (precondition): Hvad skal være sandt, inden use casen starter
  • Hovedscenarie: Trinene i den normale forløb (happy path)
  • Alternativt scenarie: Hvad sker der, når noget går galt
  • Efterbetingelse (postcondition): Hvad er sandt, efter use casen er gennemført

Gennemgang af UC3: Forkorte URL

Forudsætning: Brugeren er logget ind (har et JWT-token).

Trin 1–2: Brugeren taster en URL og klikker "Forkorte" i React-frontendet.

Trin 3: Frontend sender en POST-request til /api/urls/shorten med JWT-tokenet i Authorization-headeren.

Trin 4: Backend genererer et tilfældigt 6-tegns short code via Math.random().toString(36).substring(2,8).

Trin 5: Backend gemmer original_url, short_code og user_id i databasen.

Trin 6: Det korte link vises for brugeren.

Alternativt (4a): Hvis brugeren valgte et custom alias der allerede er i brug, returnerer databasen en uniqueness-fejl (SQL-fejlkode 23505), og systemet viser "Det alias er allerede taget".

Til eksamen:

"Use case modellen viser, hvad systemet kan gøre set fra brugernes perspektiv. Den siger intet om implementeringen — kun hvem der kan gøre hvad. Aktørerne er Gæst, Bruger og Admin. UC3 er forkorte URL — her kræves det, at man er logget ind."

Domænemodel

Domænemodellen viser de vigtigste begreber (koncepter) i problemdomænet og relationerne imellem dem. Det er ikke en database og ikke en klasse i koden — det er en beskrivelse af virkeligheden.

Forskel: Domænemodel vs. klassediagram vs. ER-diagram

DiagramHandler omNiveau
DomænemodelVirkelighed — begreber og relationer i problemdomænetAnalyse

De fire begreber i domænemodellen

  • Bruger: En person der har oprettet en konto. Har navn, email, adgangskode, admin-flag og pro-flag.
  • URL: Et forkortet link. Har original URL, short code, alias, klik-tæller, udløbsdato og evt. adgangskode.
  • KlikHændelse: En registrering af at nogen klikker på et link. Gemmer tidspunkt, referrer og enhed.
  • AdgangskodeNulstilling: Et midlertidigt token der bruges, når brugeren glemmer sit password.

Relationerne

  • Bruger ejer 0..* URL'er: En bruger kan have mange links (eller ingen). Et link tilhører præcis én bruger.
  • URL genererer 0..* KlikHændelser: Hvert klik på et link opretter en ny KlikHændelse.
  • Bruger anmoder om 0..1 AdgangskodeNulstilling: En bruger kan have ét aktivt reset-token ad gangen.

Til eksamen:

"Domænemodellen viser de fire centrale begreber i systemet. En bruger ejer mange links. Hvert klik på et link registreres som en KlikHændelse — det er det der giver statistikken. Modellen er uafhængig af implementering — den beskriver domænet, ikke koden."

Aktivitetsdiagram 1: Forkorte URL

Viser hvad der sker, når nogen åbner et kort link (shr.dk/r/abc123):

  2. Beslutning: Fandt vi short code i databasen? Nej → /not-found
  3. Beslutning: Er linket udløbet? Ja → /not-found?reason=expired
  4. Beslutning: Er linket password-beskyttet? Ja → /password/code
  5. Gem click_event med referrer og user-agent
  6. Opdater klik-tæller
  7. HTTP 302 redirect til original URL

Til eksamen:

"Aktivitetsdiagrammet for redirect viser tre mulige fejlsituationer: linket findes ikke, linket er udløbet, eller linket kræver adgangskode. I alle tre tilfælde redirectes brugeren til en fejlside. Hvis ingen af disse gælder, registreres klikket og brugeren sendes videre."

Systemsekvensdiagrammer (SSD)

Et systemsekvensdiagram viser den tidsmæssige rækkefølge af beskeder (kald) mellem aktører og systemet i ét scenarie fra en use case. Det viser præcist hvad der sker, og i hvilken rækkefølge.

SSD 1: Registrer konto — gennemgang

  1. Brugeren udfylder formularen og klikker "Opret"
  2. Frontend sender POST /api/auth/register med navn, email og password til backend
  3. Backend spørger databasen: "Findes der allerede en bruger med den email?"
  4. Databasen svarer: tomt resultat (ingen bruger fundet)
  5. Backend hasher passwordet med bcrypt: bcrypt.hash(password, 10)
  6. Backend indsætter den nye bruger i databasen
  7. Backend genererer et JWT-token: jwt.sign({userId}, JWT_SECRET, {expiresIn:'7d'})
  8. Backend sender token + brugerinfo tilbage til frontend
  9. Frontend gemmer token i localStorage og sender brugeren til dashboard

SSD 2: Forkorte URL — gennemgang

  1. Bruger klikker "Forkorte" i frontend
  2. Frontend sender POST /api/urls/shorten med Authorization: Bearer <token>
  3. Backend verificerer JWT-tokenet og henter userId
  4. Backend genererer short_code: Math.random().toString(36).substring(2,8)
  5. Backend indsætter linket i databasen med original_url, short_code, user_id
  6. Backend sender det gemte link tilbage
  7. Frontend viser det korte link til brugeren

SSD 3: Redirect — gennemgang

  1. Besøgende åbner shr.dk/r/abc123
  2. Backend slår short_code op i databasen
  3. Database returnerer linkets data (original URL, udløbsdato, password-hash)
  4. Backend tjekker udløbsdato og password — ingen begrænsninger
  5. Backend opdaterer klik-tæller og gemmer click_event
  6. Backend sender HTTP 302 redirect → original URL

Til eksamen — forskel på SSD og aktivitetsdiagram:

"Aktivitetsdiagrammet viser flowet i en proces — beslutninger og forgreninger. Systemsekvensdiagrammet viser hvem der taler med hvem og hvornår — den præcise kommunikation mellem frontend, backend og database over tid."

Afsnit 9

Systemarkitektur

Systemarkitekturen viser, hvordan systemets komponenter er organiseret og kommunikerer med hinanden. shr.dk bruger en klassisk 3-lags arkitektur.

De tre lag

LagTeknologiAnsvar
PræsentationslagReact + Vite (Vercel)Det brugeren ser. Sider, formularer, knapper. Ingen forretningslogik.
ApplikationslagNode.js + ExpressForretningslogikken. Validering, JWT-check, generering af short codes, email-afsendelse.
DatalagPostgreSQLLagring og hentning af data. Tabeller: users, urls, click_events, password_reset_tokens.

Kommunikation mellem lagene

  • Frontend → Backend: HTTP REST API. JSON sendes frem og tilbage. Frontend ved ikke noget om databasen.
  • Backend → Database: pg.Pool (PostgreSQL driver). Parameteriserede SQL-queries.
  • Autentificering: JWT-token sendes i Authorization: Bearer <token> headeren ved hvert kald til beskyttede endpoints.

Middleware-kæden i Express

En request til et beskyttet endpoint går igennem flere led:

Request → verifyToken middleware → [verifyAdmin middleware] → Route handler → Database → Response

Middleware er en funktion der kører mellem request og response. Den kan afvise requests (401/403) eller tilføje data til request-objektet (fx req.userId).

Hvorfor 3-lags arkitektur?

Det adskiller ansvarsområder. Frontend ved ikke, hvordan data gemmes. Backend ved ikke, hvordan data vises. Databasen ved ikke, hvad brugeren gør. Det gør det lettere at ændre ét lag uden at ødelægge de andre.

Til eksamen:

"Systemet er bygget som en 3-lags arkitektur. Frontend er React deployet på Vercel og kommunikerer kun med backend via HTTP. Backend er Node.js/Express og håndterer al forretningslogik. Databasen er PostgreSQL og indeholder fire tabeller. Lagene er adskilt, så de ikke kender til hinandens implementering."

Afsnit 10

Design

Designklassediagram

Hvad viser et designklassediagram?

Det viser softwarens klasser (eller i Node.js: moduler/objekter), deres attributter, metoder og relationer. Det er tættere på koden end domænemodellen.

I rapporten vises backend-klasserne: ExpressApp, AuthRouter, UrlRouter, AdminRouter, VerifyTokenMiddleware og Pool.

Design Patterns brugt i projektet

Middleware Pattern (Chain of Responsibility):

Når en request kommer ind til et beskyttet endpoint, kædes middleware-funktioner:

app.use('/api/urls', verifyToken, urlRoutes) // verifyToken kører FØRST → tjekker JWT // Hvis token er gyldigt → går videre til urlRoutes // Hvis token er ugyldigt → stopper her med 401

Det er Chain of Responsibility: hvert led i kæden bestemmer, om det videresender requesten.

Singleton Pattern:

PostgreSQL-poolen oprettes én gang og deles af alle routes:

// Db.js — oprettes én gang, exporteres til alle routes const pool = new Pool({ connectionString: ... }) module.exports = pool

MVC-inspireret struktur:

Koden er opdelt i: routes/ (controllers), middleware/, Db.js (model). Ansvar er adskilt.

Til eksamen:

"Jeg har brugt Middleware Pattern til autentificering — det er en form for Chain of Responsibility. En request til /api/urls skal igennem verifyToken-middleware, som tjekker JWT-tokenet, inden den når routeren. Det giver genbrugelig autentificering på tværs af alle beskyttede endpoints."

Afsnit 11

Database Design

ER-diagram

Hvad er et ER-diagram?

ER = Entity-Relationship. Diagrammet viser databasens tabeller (entities) og relationerne imellem dem via fremmednøgler.

De fire tabeller

users

  • id — primærnøgle, auto-increment
  • email — UNIQUE constraint, man kan ikke have to konti med samme email
  • password_hash — bcrypt-hash, aldrig klar tekst
  • is_admin, is_pro — boolean flags til roller

urls

  • user_id — fremmednøgle til users.id. Et link tilhører én bruger.
  • short_code — UNIQUE. To links kan ikke have samme kode.
  • expires_at — nullable. NULL betyder "udløber aldrig".
  • password_hash — nullable. NULL betyder "ikke password-beskyttet".
  • clicks — tæller hvor mange gange linket er brugt (opdateres ved redirect).

click_events

  • url_id — fremmednøgle til urls.id. Hvert klik hører til ét link.
  • referrer — hvilken side brugeren kom fra (kan være NULL).
  • user_agent — browserens user-agent string (bruges til at detektere mobil/desktop).

password_reset_tokens

  • Bruges til "Glemt adgangskode" flowet. Et token genereres, sendes via email, og bruges én gang.
  • used — boolean. Når tokenet er brugt, markeres det som brugt så det ikke kan genbruges.
  • expires_at — tokenet udløber efter 1 time.

Primærnøgler og fremmednøgler

Primærnøgle (PK): En kolonne der entydigt identificerer hver række i en tabel. I alle tabeller er det id med SERIAL (auto-increment).

Fremmednøgle (FK): En kolonne der refererer til primærnøglen i en anden tabel. urls.user_id refererer til users.id. Det sikrer at man ikke kan have et link, der tilhører en bruger der ikke eksisterer.

Hvorfor PostgreSQL og ikke fx SQLite?

PostgreSQL er valgt fordi datamodellen er klart relationel — links tilhører brugere og klik tilhører links. PostgreSQL understøtter fremmednøgler, UNIQUE constraints og komplekse SQL-queries (fx GROUP BY og INTERVAL) som bruges i statistik-endpointet. SQLite er simplere men ikke egnet til produktion med concurrent brugere.

Til eksamen:

"Databasen har fire tabeller. urls.user_id er en fremmednøgle til users.id — det sikrer at hvert link tilhører en bruger. click_events.url_id er en fremmednøgle til urls.id — det giver mulighed for at hente alle klik for et specifikt link, som brugt i statistik-endpointet."

Afsnit 12

Implementation

Database forbindelsen (Db.js)

Hvad gør Db.js?

Opretter én pg.Pool-forbindelse til PostgreSQL. Pool betyder, at den holder flere åbne forbindelser klar, så mange requests kan køre parallelt uden at vente på hinanden.

Den tjekker om DATABASE_URL miljøvariablen er sat (som den er på Vercel/cloud) — ellers bruger den separate host/port/database variabler (lokal udvikling).

JWT Middleware

Hvad sker der i verifyToken?

// Henter token fra "Authorization: Bearer <token>" headeren const token = req.headers['authorization']?.split(' ')[1] // jwt.verify() dekoder tokenet og tjekker signaturen // Hvis tokenet er ændret eller udløbet → fejl → 401 const decoded = jwt.verify(token, process.env.JWT_SECRET) // Gem userId på request-objektet, så næste funktion kan bruge det req.userId = decoded.userId next() // Gå videre til næste middleware/route

JWT = JSON Web Token. Det er en signeret streng opdelt i tre dele: header, payload og signature. Man kan ikke ændre payload'en uden at ugyldiggøre signaturen — det er det der gør det sikkert.

Redirect-endpointet

Det vigtigste endpoint i hele systemet

Dette endpoint håndterer al trafik til korte links. Det er det eneste offentlige endpoint (kræver ikke JWT). Det:

  1. Slår short_code op i databasen
  2. Tjekker tre betingelser: ikke fundet / udløbet / password-beskyttet
  3. Gemmer click_event med referrer og user-agent
  4. Opdaterer klik-tæller
  5. Sender HTTP 302 redirect

HTTP 302 betyder "midlertidig omdirigering". Browseren følger automatisk Location-headeren til den nye adresse.

Short code generering

Hvordan genereres short codes?

const short_code = custom_alias || Math.random().toString(36).substring(2, 8)

Math.random() genererer et tal mellem 0 og 1, fx 0.7823456.

.toString(36) konverterer til base-36 (0-9 og a-z), fx "0.r2x4k9".

.substring(2, 8) tager 6 tegn efter "0.", fx "r2x4k9".

Resultatet er en 6-tegns alphanumerisk kode. Hvis brugeren har valgt et custom alias, bruges det i stedet.

bcrypt og password-sikkerhed

Hvorfor bcrypt?

bcrypt er en hash-funktion designet til adgangskoder. Den er bevidst langsom (salt rounds = 10 betyder 2^10 = 1024 iterationer) for at gøre brute-force angreb dyre.

Adgangskoden gemmes aldrig i klar tekst. Kun hashen gemmes. Ved login bruges bcrypt.compare(inputPassword, storedHash) — det sammenligner uden at "dehashes".

Til eksamen:

"Short codes genereres tilfældigt med Math.random() konverteret til base-36, som giver 6 alfanumeriske tegn. Adgangskoder hashes med bcrypt inden de gemmes — det er et krav fra IFK-01. JWT-tokenet bruges til at identificere brugeren ved hvert API-kald — middleware verificerer tokenet og lægger userId på request-objektet."

Afsnit 13

Test

Teststrategier

Black-box test (funktionel test)

Man tester et endpoint uden at kende den interne implementering. Man sender et input og tjekker output. Det er det der bruges til API-test i rapporten — send en HTTP-request, tjek HTTP-statuskode og svaret.

Grænseværditest

Tester ved kantsituationer — hvad sker der ved udløbne links (TC-10), forkerte adgangskoder (TC-13), manglende token (TC-06)? Disse er vigtige fordi de fleste fejl opstår i grænsetilfælde.

Sikkerhedstest

  • ST-01 SQL Injection: Input ' OR 1=1; -- i email-feltet. Parameteriserede queries ($1, $2...) forhindrer det — inputtet behandles som data, ikke som SQL-kode.
  • ST-02 JWT-manipulation: Ændres payload-delen af et token, ugyldiggøres signaturen. jwt.verify() afviser det.
  • ST-04 Adgangskontrol: Man kan kun slette sine egne links fordi SQL-queriet indeholder WHERE id=$1 AND user_id=$2 — begge skal matche.

Sammenhæng: krav → test

Hvert test case er koblet til et funktionelt krav:

  • FK-03 (forkorte URL) → TC-05 (gyldig URL + JWT → 201), TC-06 (ingen JWT → 401)
  • FK-04 (redirect) → TC-08 (gyldigt link → 302), TC-09 (ikke-eksisterende → /not-found)
  • IFK-03 (SQL-sikkerhed) → ST-01 (injection forsøg afvises)

Til eksamen:

"Alle testcases er black-box tests — jeg tester endpointets adfærd udefra. TC-12 tester at man ikke kan slette en anden brugers link. Det er fordi SQL-queriet kræver at både id OG user_id matcher. Selv om man kender ID'et på et fremmed link, kan man ikke slette det."

Teknologivalg

Spørgsmål du kan få til eksamen

"Hvorfor Node.js og ikke fx Java?"
JavaScript bruges allerede på frontend (React), så én teknologistak giver ensartet erfaring og fælles viden om asynkron programmering. Node.js er desuden velegnet til I/O-tunge applikationer som API-servere.

"Hvorfor JWT og ikke sessions?"
JWT er stateless — serveren gemmer intet om sessioner. Tokenet indeholder al nødvendig information (userId) og er kryptografisk signeret. Det fungerer godt med en separat frontend deployet på Vercel, da der ikke er delt server-state.

"Hvorfor PostgreSQL og ikke MongoDB?"
Datamodellen er klart relationel: brugere ejer links, links genererer klik-hændelser. Relationelle databaser med fremmednøgler og JOIN er velegnet til dette. MongoDB (NoSQL) passer bedre til ustrukturerede eller dokumentbaserede data.

"Hvad kunne gøres bedre?"
Tests burde have været skrevet løbende (TDD). Input-validering på URL-feltet mangler. Statistik-komponenten var den mest tidskrævende del — den kunne have været prioriteret anderledes i sprint-planlægningen.

Scrum i soloprojekt

Hvad fungerede / hvad fungerede ikke?

Fungerede godt: Sprint-strukturen gav naturlige checkpoints og tvang til prioritering. Sprint 0 til analyse sikrede, at koden ikke startede på usikker grund.

Fungerede mindre godt: De sociale aspekter af Scrum (teamkoordination, standups) er meningsløse i et soloprojekt. Burndown-chartet er mere nyttigt i et team, hvor man kan se om andre er bagud.
